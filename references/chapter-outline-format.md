# 用户可见章纲格式 — 逐章剧情梗概

## 1. 核心定义

用户可见的“章纲”是逐章剧情梗概，不是字段表、任务卡、审计表或制作参数清单。

每章用“章节标题 + 连贯剧情梗概”的形式写清本章从开头到结尾将发生什么，让用户不阅读正文也能判断剧情是否成立，并让后续正文可以直接据此展开。

用户可见章纲必须优先回答：
- 这一章从什么状态开始；
- 主要人物做了什么；
- 冲突、发现、误会、反转或关系变化如何发生；
- 关键设定、系统提示、数值变化或伏笔如何进入剧情；
- 本章最后停在什么状态，怎样承接下一章。

## 2. 默认展示格式

单个章纲范围使用：

```text
每章基本大纲（第1-6章）

第1章：<有吸引力的标题>
<用一段或数段连贯中文，按剧情发生顺序写出本章主要内容。>

第2章：<有吸引力的标题>
<继续写本章主要内容。>
```

章节标题使用“第X章：标题”。冒号保留。

## 3. 叙述方式

用户可见章纲必须：
- 使用自然中文连续叙述，不拆成大量字段；
- 按实际剧情顺序写，不只列关键词；
- 主要事件要有因果，不写成互不相干的事件清单；
- 必须写到本章结尾状态或章末钩子；
- 重大数值、身份、规则、系统任务、能力变化若影响剧情，直接写进梗概；
- 关键人物的态度变化要写出触发原因，不能只写“好感提升”“关系改善”；
- 有声项目可在梗概中写清关键“听觉事件”，但不要把声效标签、CV提示和制作清单塞进用户可见章纲；
- 不必写成文学正文，不展开完整对白，不堆修辞；重点是具体、清楚、可执行。

## 4. 详细程度

章纲详细度以“足以指导后续正文、不替代正文”为准，不设统一字数硬阈值。

简单过渡章可以较短；包含多次反转、战斗、重大信息释放、关系变化或系统结算的章节应写得更详细。

不要为了凑长度重复解释同一个事件。

## 5. 用户可见内容中禁止出现的默认字段堆叠

除非用户明确要求表格化章纲，否则不要向用户交付下面这种格式：

```text
本章功能：
承接状态：
核心事件：
核心冲突：
信息释放：
人物推进：
开启伏笔：
推进伏笔：
回收伏笔：
结尾承接：
```

这些结构化字段可以作为内部执行元数据使用，但不得替代用户可见的逐章剧情梗概。

## 6. 内部执行元数据

为保证长篇一致性，Skill 可以从已确认的逐章剧情梗概中派生内部执行元数据，包括：
- 章节编号；
- 视角人物；
- 章节功能；
- 承接状态；
- 核心冲突；
- 信息释放；
- 人物与关系变化；
- 伏笔开启、推进、回收；
- 物品、能力、位置、时间变化；
- 章末状态；
- 禁止提前发生事项；
- 有声化执行要点；
- 作品配置约束。

内部执行元数据是从章纲梗概派生的执行辅助，不是第二套规划真相。若二者冲突，以用户已批准的逐章剧情梗概为准，并重新生成内部元数据。

## 7. 修改规则

用户修改章纲时：
1. 先修改用户可见的逐章剧情梗概；
2. 标记最早受影响章节；
3. 重新派生受影响区间的内部执行元数据；
4. 重新做局部章纲审计；
5. 重新导出章纲 DOCX；
6. 已生成正文按回滚协议判断是否需要复核或重写。

不要只改内部字段而保持用户可见剧情梗概不变。
